# ADR 0004 — Development and deploy workflow

- **Status:** Accepted, 2026-09-03
- **Deciders:** Stephen
- **Related:** ADR 0002 (deploy target), STE-25, STE-29, STE-30, STE-52

## Context

Single user, invite-only, behind an auth gate. Seven working days to MVP. Most code is generated by a
coding agent. The sabbatical's stated goal includes learning modern Git and AI-assisted development, so the
process is part of the deliverable rather than overhead around it.

The question was whether to push every change straight to production — nobody else can reach the app, so a
broken deploy harms no one — or to build and test locally first and deploy deliberately.

**"Behind a login gate" is a real argument, and it is void.** The gate protects other people from seeing a
broken app; there are no other people, so that concern genuinely does not apply. But it was never the
expensive risk. Three costs remain, and the gate mitigates none of them:

1. **Debug loop speed.** Finding a break in production means debugging a deployed app. With an agent
   generating code, loop speed is the largest single determinant of throughput in a seven-day window.
2. **The database.** A destructive migration against live Supabase is the one mistake here that is not
   cheaply reversible.
3. **The API bill.** Objective 2.2 puts an unbounded cash cost on getting access wrong. A runaway loop
   against a live key does not care that nobody can log in.

## Decision

**Local-first inner loop, continuous deploy on merge. No staging environment.**

1. Develop locally against a **separate dev Supabase project**. The agent iterates here.
2. **One branch per slice**, named from its Linear issue (`stephenpollock/ste-60-engine-…`).
3. **Tests run locally before push** — the engine unit tests above all, which is why the engine is a
   headless slice.
4. **Push → PR → CI runs tests → human review → merge.**
5. **Merge to `main` auto-deploys to Railway.** One slice, one squashed commit, one deploy.

Trunk-based development with short-lived branches. Squash-merging is not cosmetic: it makes `main` a
readable list of slices and makes rollback a single `revert`.

### Two databases

`fpl-advisor-dev` and `fpl-advisor-prod` as separate Supabase projects. Sharing one means every schema
experiment mutates the real database, row-level security cannot be tested in isolation, and test data ends
up in production without anyone noticing. Migrations run against dev first.

Local Supabase in Docker is cleaner still and was rejected on setup cost for this week only — a second cloud
project buys most of the benefit for a fraction of the day-one time.

### Migrations are the strict part

Additive, checked in, dev first, never through the Supabase console. Row-level security policies ship in the
same migration that creates the table they protect (F7-AC-11), and that is asserted by a test rather than
trusted.

### Reviewing agent-written code

The pull request is where human judgement actually lands, and it is the first thing skipped under time
pressure. Reading a whole generated diff and forming an impression does not work and should not be
attempted.

**Instead: require the agent to state what changed and why as numbered, individually falsifiable claims, and
rule on those.** This is the `agent-qa-loop` division of labour applied to the PR — the agent knows what it
built, the human keeps judgement but keeps it specific. It is the same technique already used on the spec
review and the overnight PRD critique, both of which produced numbered rulings rather than a verdict.

## Consequences

- The loop is fast where speed matters (local iteration) and deliberate where mistakes are expensive
  (migrations, merges to main).
- Production is always the latest merged slice. There is no "ready to deploy but not deployed" state to
  track, and no environment drift to reason about.
- **Rollback is redeploying Railway's previous deployment.** That is the entire safety net, so it gets
  tested once on day one while nothing depends on it — not discovered on the 10th.
- A second Supabase project has to exist before the first migration, not after.
- Deliberately not built: a staging environment, release branches, gitflow, or a manual gate before every
  merge. Per-slice manual checklists cover verification at slice level, which is where it belongs.
